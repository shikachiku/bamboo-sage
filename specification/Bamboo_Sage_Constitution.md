1. Bamboo Sage の目的

Bamboo Sage は、

長期運用を前提とした

個人専用の投資判断支援システムである。

売買を自動化することは目的としない。

最終的な投資判断は

必ず人間が行う。


2. 開発理念

Bamboo Sage は

以下を最優先とする。

・シンプル

・保守しやすい

・長期間運用できる


コードを書く前に

設計を考える。


コードより設計を優先する。


3. 開発環境

標準環境

・Chromebook

・Linux (Penguin)

・Python

・VS Code


Windowsでも動作できる構造を目指す。


4. プログラム管理

ソースコードは

GitHub

で管理する。


Git により

変更履歴を管理する。


大きな修正を行う前には

必ずコミットを作成する。


5. データ管理

運用データは

Google Drive

で管理する。


データ保存先は

config

で一元管理する。


ソースコードへ

保存先を直接記述しない。


RAWデータは資産である。


RAWデータは削除しない。


6. 時間足

TradingView から取得した


・4時間足

・日足

・週足

・月足


を

RAWデータとして保存する。


時間足は生成しない。


保存したRAWデータを

すべての処理で利用する。


7. データ構造

運用データは

Google Drive

の

data/

以下で管理する。


データは

銘柄ごとにフォルダを作成する。


標準構造は


data/
└── 銘柄/
    ├── raw/
    │   ├── 4H.csv
    │   ├── 1D.csv
    │   ├── 1W.csv
    │   └── 1M.csv
    │
    └── indicator/
        ├── adx/
        │   ├── 4H.csv
        │   ├── 1D.csv
        │   ├── 1W.csv
        │   └── 1M.csv
        │
        ├── heikin_ashi/
        ├── highlow/
        ├── highlow5/
        ├── trend/
        ├── strategy/
        └── ...


RAWデータは

TradingViewから取得した


4時間足

日足

週足

月足


を保存する。


すべてのインジケータは

indicator/

以下へ保存する。


新規プログラムおよび既存プログラムは

このフォルダ構成へ統一する。


8. インジケータ

インジケータは

各時間足ごとに作成する。


作成したデータは

保存して利用する。


必要なプログラムは

保存済みデータを読み込む。


標準データアクセス方式は

DOWNLOAD_HISTORY.py

と同じ方式を採用する。


新規プログラムは

この方式で作成する。


既存プログラムは

順次この方式へ統一する。


9. バックテスト

バックテストは

保存済みの


RAWデータ

および

インジケータデータ


を利用する。


バックテスト専用データは

作成しない。


10. フォルダ構成

bamboo-sage/

11. パス

絶対パスを

ソースコードへ記述しない。


保存先は

config

から取得する。


保存先を変更する場合は

設定のみ変更する。


12. コーディング方針

関数は

一つの役割だけを持つ。


コードは

短く

読みやすく

保守しやすく作成する。


コメントは

処理内容ではなく

理由を書く。


13. 開発ルール

新しい機能を追加する前に

この憲法を確認する。


設計変更が必要な場合は

憲法を更新する。


コードより

憲法を優先する。


既存プログラムを修正する場合は

Bamboo Sage の標準構造へ

順次統一する。


14. コード修正ルール（最重要）


Bamboo Sage のコード修正では、

変更範囲を明確にする。


修正対象は必ず明示する。


例：

・修正対象：
def rma()


・修正対象：
def calculate()


・修正対象：
adx.py 全体


など。


コード修正方法は、

修正内容に応じて選択する。



【小規模修正】

1つまたは少数の関数変更の場合、

対象def単位で提示する。


例：

def calculate():

    修正後コード

    return result



【大規模修正】

処理構造変更、

複数関数への影響、

ファイル全体の整合性確認が必要な場合は、

ファイル全体コードを提示する。


ファイル全体コードの提示は禁止しない。


むしろ、

以下の場合は積極的に利用する。


・コピー置換する場合

・バックアップを作成する場合

・既存構造を確認する場合

・複数箇所を修正する場合



【修正時の説明】

コード提示前に必ず説明する。


説明内容：

・変更理由

・変更箇所

・既存仕様への影響

・確認方法



【修正手順】

修正は以下の順番で行う。


1.

設計確認


2.

修正内容提示


3.

コード反映


4.

プログラム実行


5.

結果確認


6.

必要なら追加修正



原因追跡できる状態を維持する。



【禁止事項】

以下を勝手に変更しない。


・不要なimport変更

・フォルダ構造変更

・関数名変更

・データ形式変更

・既存仕様の変更


必要な場合は理由を説明し、

確認後に変更する。



【目的】

Bamboo Sage は

長期運用を前提とする。


そのため、


小さな変更でも原因追跡できること、


変更履歴を明確にできること、


既存機能を壊さないこと


を最優先とする。


コード量より

保守性を優先する。



15. Version 管理


憲法は

Bamboo Sage の

最上位設計書である。


設計変更を行った場合は

Version を更新する。


すべてのプログラムは

この憲法に従って開発する。
